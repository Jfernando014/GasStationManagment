# SCRUM-38 — Dominus cash complement

## Scope and placement

Stateless PDF generation in `sales`, independent of `JournalService`, `CashService`,
repositories and the future cash closing module. No totals, subtotals, balances or
relationships between sections are calculated or reconciled. Intentionally
inconsistent caller-supplied totals are rendered unchanged.

The local `docs/references/dominus-tabla-referencia.png` was visually inspected.
It is reference material only and is not part of this delivery. The two local Excel
workbooks were also inspected: `Historias Usuario Estacion.xlsx` describes the
broader future workflow (HU-44), and the objectives workbook contains sales targets,
not this cash table. The screenshot supplies the detailed layout for this ticket.
Saving the final PDF in a journal, mentioned by the broader story, is outside the
explicit SCRUM-38 scope. No original Dominus PDF was available; tests generate a
minimal two-page original. The JSON fixture reproduces the amounts visible in the
screenshot; it is test data only. All local reference files remain untouched.

The backend previously had Apache POI for Excel and no PDF library. PDF operations
use [Apache PDFBox 3.0.8](https://pdfbox.apache.org/download.cgi), under the
[Apache License 2.0](https://pdfbox.apache.org/). Java 21 and the existing Spring
Boot version are retained. No additional image codecs, external fonts or PDF services
are needed.

## Endpoint

`POST /api/v1/sales/dominus/cash-complement`

Use the existing Bearer JWT and `ADMIN` authority. The controller uses the existing
`SalesAdminAuthorization` guard because method-security annotations are not enabled
in this project. The existing security chain rejects unauthenticated requests with
403; authenticated users without `ADMIN` also receive 403.

Multipart parts:

| Part | Content type | Value |
| --- | --- | --- |
| `file` | `application/pdf` | Nonempty original file with `.pdf` extension, at most 25 MiB |
| `data` | `application/json` | `DominusCashComplement` object below |

Response: `200 application/pdf`, attachment
`dominus-YYYY-MM-DD-complemento.pdf`, with content length and `Cache-Control: no-store`.
The operation does not store uploads or generated files.

From the repository root, using the sample original generated by the tests:

```powershell
curl.exe -X POST "http://localhost:8080/api/v1/sales/dominus/cash-complement" `
  -H "Authorization: Bearer YOUR_TOKEN" `
  -F "file=@backend/target/dominus-demo/original.pdf;type=application/pdf" `
  -F "data=@backend/src/test/resources/dominus/cash-complement.json;type=application/json" `
  --output "backend/target/dominus-demo/download.pdf"
```

This HTTP example assumes a backend already running with its normal environment;
the automated tests below do not start that backend or access its database.

## Input contract

`sales/domain/models/DominusCashComplement.java` is an immutable record-based input
DTO with nested typed records and Jakarta Bean Validation, shared by REST and the
application service. It has no Excel or PDF types. The renderer is a separate class
in `sales/infrastructure/export`, so its provisional layout can change independently.

Every section and fixed `Values` object is required. Lists are required, may be
empty, and retain caller order. Null list entries are rejected. Each list accepts
at most 20 rows, subject to the single-page layout limit described below.

| Section | Fields |
| --- | --- |
| `header` | `reportDate` (ISO date), `stationCode` (code only, e.g. `761`), `stationName`, optional `administrator` |
| `lubricantSales` | `oils`, `additivesWaterLiquids`, `miscellaneousGoods`, `additionalRows`, `total` |
| `creditSales` | `sotracauca`, `puntosColombia`, `additionalRows`, `total` |
| `expenses` | `rows`, `total` |
| `deposits` | `credibanco`, `bancolombiaPrimax`, `qr`, `additionalRows`, `total` |
| `dailyBalance` | `dailySales`, `expenses`, `credibancos`, `credits`, `qr`, `dailyCash` |
| `accumulatedCash` | `previousCash`, `dailyCash`, `deposit`, `accumulatedBalance` |

Fixed named concepts receive a `Values` object. Additional/expense rows receive
`{"concept": "...", "values": {...}}`.

```json
{
  "detail": "Optional text in the middle column",
  "intermediateAmount": null,
  "amount": 123456.78
}
```

The three visible columns are concept, middle detail/intermediate amount, and final
amount. `detail` and `intermediateAmount` are alternatives for the same middle cell;
supplying both nonblank detail and an intermediate amount is rejected. Each cell
is independent. All three `Values` fields are optional: `{}` means a blank row value.
`concept` may also be null or empty for a blank row. Text is limited to 80 characters
(station code: 30). The title `DOMINUS` and fixed row labels belong to the template.

All monetary fields are `BigDecimal`: up to 12 integer digits and 2 fractional
digits, including zero and negatives. Monetary cells may be null (blank). Section
totals and every field in `dailyBalance` and `accumulatedCash` are required. Missing
totals are never inferred. Formatting uses Colombian separators, preserves the
supplied decimal scale, and never converts money through `double`.

The complete request is in
[`cash-complement.json`](../backend/src/test/resources/dominus/cash-complement.json).
The two `dailyCash` fields, all QR/credit/expense values and every section total
remain separate even when their sample amounts coincide.

## PDF generation and provisional layout

The service validates the DTO even when invoked directly. It parses the original
PDF in strict mode, rejects unreadable, encrypted or pageless documents, appends a
single A4 landscape page and saves the document to memory. It keeps the original
page streams, dimensions, rotations, resources and order. The PDF container is
reserialized; the output is not byte-identical to the original file. All PDF
documents, input buffers, page content streams and output streams are closed.

The supplement follows the screenshot: header above the left table; three columns
on the left; daily balance and accumulated cash on the right; centered section
headings, visible borders, right-aligned monetary cells, yellow section totals and
pale yellow accumulated balance. The middle columns remain visible when empty.
The template preserves at least:

- 3 lubricant/accessory rows, followed by any additional rows.
- Sotracauca, Puntos Colombia and 2 available credit rows.
- 7 expense rows.
- Credibanco, Bancolombia Primax, QR and 1 available deposit row.
- 1 blank accumulated cash row before the accumulated balance.

Supplied rows fill available positions in order. Padding adds empty presentation
cells only; it does not create monetary data. Extra rows are retained. Text wraps
within measured cells at a fixed 10-point font. The complete layout is measured
before a page is added; content that cannot fit is rejected with 422, without
clipping, truncation, shrinking the text or adding another page.

This is a provisional approximation, not a confirmed client form. It uses Helvetica
with Spanish/Western European characters. Characters unsupported by this font are
rejected with 422. A large number of extra rows or long text can exceed the single
page even within DTO length limits. PDF/A conformance and preservation of digital
signature validity are not provided. Encrypted originals are deliberately rejected.

## Errors

Errors follow the module's `ProblemDetail` convention (`code`, `detail`, `status`;
validation errors also include field paths).

| Status | Examples |
| --- | --- |
| 400 | `DOMINUS_EMPTY`, `DOMINUS_INVALID_PDF`, `DOMINUS_INVALID_DATA`, `MISSING_REQUEST_PART`, `MALFORMED_REQUEST`, `VALIDATION_ERROR` |
| 403 | Existing security chain or `ACCESS_DENIED` |
| 413 | `DOMINUS_TOO_LARGE`; existing servlet limits remain 25 MB/file, 26 MB/request |
| 415 | `DOMINUS_UNSUPPORTED_TYPE`, `UNSUPPORTED_MEDIA_TYPE` |
| 422 | `DOMINUS_LAYOUT_OVERFLOW` |
| 500 | `DOMINUS_GENERATION_FAILED` |

## Verification and demonstration

Run from `backend`:

```powershell
mvn -B "-Dtest=DominusPdfServiceTest,DominusPdfControllerTest" test
```

These are plain service tests and an MVC slice using the actual JWT filter and
security configuration. No datasource, JPA repositories, Flyway migrations or
development database are initialized. Tests verify original-page streams and
rendered pixels, page order/count/geometry/rotation, all sections, blank grid cells,
middle amounts/details, extra rows, independent supplied totals, decimal precision,
negative/zero values, invalid requests/files, authorization, and layout errors.
Glyph bounds must lie inside their cells and page margins without overlapping
other glyphs. Both the reference fixture and a longer-text case are checked.
Concurrent requests are also checked with separate amounts and shared service use.

Final validation on Java 21: compilation of the backend and tests succeeded;
**25 tests passed, 0 failures, 0 errors, 0 skipped** (18 SCRUM-38 tests and 7 existing
`JournalFileServiceTest` / `JournalFileControllerTest` regression tests). The final
Maven selection included these four classes. `git diff --check` and whitespace
checks on the newly created sources passed. There is no configured formatter or
Checkstyle plugin in the backend. The generated previews were visually inspected.

Generated local artifacts (ignored by Git):

- `backend/target/dominus-demo/original.pdf`: generated two-page input.
- `backend/target/dominus-demo/dominus-complement.pdf`: three-page result.

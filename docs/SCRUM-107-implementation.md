# SCRUM-107 — shift sales history

## Storage introduced in increment 2

The statistics module owns immutable shift sale snapshots. Its internal ShiftSaleHistoryRepository port accepts
already resolved domain values. Increment 3 adds the application service described below, using the existing
public SellerCloseQuery and DayStaffQuery contracts. Increment 4 connects the public closing event and supplies
explicit recovery; no HTTP endpoint is introduced.

V33 adds statistics_journal_sales and statistics_shift_sale. Only a foreign key between these two statistics
tables is used. Original vendor identifiers, resolved worker UUIDs, names, source shift names, worked codes and
effective roles are snapshots. The support flag is stored and constrained to agree with the effective role.

## Transactions and idempotency

The JDBC adapter follows existing JDBC adapters in the project. TransactionTemplate explicitly uses
REQUIRES_NEW and READ_COMMITTED. There are no mutable JPA entities or public update/delete methods.

Each write inserts the date's processing row with ON CONFLICT DO NOTHING, then locks it with SELECT FOR UPDATE.
This handles both first-insert races and existing pending days. Different dates do not share a global lock.
All sales and the PROCESSED marker commit together. An empty list commits a PROCESSED marker with sale_count 0;
it does not fabricate zero sales for scheduled workers.

A confirmed date is returned unchanged, including on repeated calls with a different payload. A late failure
cannot downgrade PROCESSED to PENDING. The database separately enforces the source business key
(journal_date, vendor_document, shift_name). No exists-before-insert check is used.

A failed storage transaction rolls back every sale. The adapter records PENDING, an attempt count and a bounded
error in a separate transaction, then rethrows the original exception. Pending dates can be read and retried by
calling the same port. If the database is unavailable, recording PENDING can also fail: that exception is attached
to the original one. Increment 4 additionally retains the durable event publication and explicitly retries it
when the processing marker could not be stored.

## Exact values

COP and gallon columns remain separate and use unconstrained PostgreSQL NUMERIC. Original decimal scales are
stored separately so even scientific notation and negative scales round-trip exactly. Values beyond PostgreSQL's
exact numeric capacity are rejected, never rounded. Signed observations remain signed; no adjustment calculation
or new adjustment policy is introduced. NaN and infinities are rejected by SQL constraints.

The original closing timestamp's whole seconds and nanoseconds are stored separately, preserving LocalDateTime
metadata beyond PostgreSQL's microsecond resolution. Processing timestamps are generated by PostgreSQL.

## Pending dependencies

Source V22 and VendorShiftCloseEntity still limit vendor_document to 30 characters while the current staff flow
can send worker UUID strings of 36 characters. Statistics stores the full identifier, but does not fix sales,
incentives or any existing migration. Increment 3 resolves full worker UUID strings against effective DayStaff
members; the public contracts do not provide cedula-to-worker lookup. Such identifiers remain explicit pending
incidents. DayStaffQuery currently omits inactive workers, and its implementation builds one effective line per
worker. A missing worker or an unsupported second shift remains pending instead of receiving an inferred role.
Retrying an unprocessed historical date still depends on the then-available sources: neither query certifies an
immutable staffing snapshot as of closedAt. Already confirmed snapshots are never rebuilt from mutable sources.

The increment 4 listener described below reuses those failure markers without counting the same failure twice.
Identity and staffing limitations remain pending incidents, with no fallback sales or inferred roles.

## Increment 3: registration from public sales and staff queries

ShiftSaleHistoryRegistrationService.registerClosedJournal accepts the existing ClosedJournalSnapshot. The caller
must already know the journal is closed; this increment does not create a listener or import sales internals.
The service uses only sales.SellerCloseQuery and shifts.daystaff.DayStaffQuery. No public contracts or migrations
were added or changed.

The service first returns a previously PROCESSED day without querying mutable sources. Otherwise it reads all
vendor closes for the operational date once. A non-null empty result is a successful empty day and needs no
staff query. A null response, null close, date mismatch or exception is a failure, never zero sales.

For nonempty sales it reads the day's staff once and requires the same operational date, CONFIRMED step 1 and
noveltiesApplied. Effective members are indexed by worker UUID; sales identifiers must be full UUID strings
(case-insensitive hex is accepted, abbreviated UUID groups and whitespace are rejected). Original vendor text
is retained unchanged. Matching requires the exact workedCode, never a name, pump, usual role or gridCode.
A role must be exactly TITULAR or APOYO. Member.support determines the stored classification, with a consistency
check against dayRole. Replacements and shift changes use the member returned after confirmed novelties.

Several closes for a seller are accepted only when every distinct shift has exactly one matching effective
member. Two matching members, repeated closes or UUID case aliases of the same worker/shift are incidents.
The consumer can handle distinct effective members if the public source provides them; it does not claim the
current one-line-per-worker producer can certify multiple worked shifts.

The four gallon observations and basketDominusAmount, dominusTirilla and totalDelivered COP observations are
copied exactly into ShiftSaleAmounts. Payment breakdowns are not added together or used to reconstruct sales.
Missing amounts fail validation rather than becoming zero. Every snapshot is built before calling saveJournal,
so one unidentified seller prevents confirmation of the whole day.

The application service suspends an ambient transaction (NOT_SUPPORTED), leaving source reads to their owners
and atomic writes to the increment 2 repository. No long database transaction or row lock surrounds external
source calls. Mapping and source failures call markPending and rethrow the original exception. Failure to record
PENDING is attached as a suppressed exception. Storage failures are already recorded by saveJournal and are not
marked a second time. If another registration confirms the date while a source query fails, its confirmed
result takes precedence and cannot be downgraded.

## Increment 4: committed events and explicit recovery

New production files, all inside statistics:

- infrastructure/listeners/JournalClosedShiftSalesListener.java
- application/ShiftSaleHistoryRecoveryService.java
- infrastructure/config/ShiftSaleHistoryRecoveryConfiguration.java

The listener consumes sales.JournalClosedEvent with @TransactionalEventListener(AFTER_COMMIT), a stable
listener id `statistics.shift-sales-history` and the default fallbackExecution=false. It copies all event
metadata into ClosedJournalSnapshot and delegates to the existing registration service. No source query or
history write runs before the source transaction commits; rolling back the closing also rolls back its durable
Modulith publication. Existing inventory and incentives listeners are unchanged.

The listener deliberately propagates processing failures. Spring logs AFTER_COMMIT failures without undoing
the committed closing. The service/repository records PENDING in its own transaction; Modulith leaves this
listener's publication incomplete. In particular, if writing PENDING also fails, the publication stored in the
closing transaction is the durable recovery record. Statistics does not assume Modulith retries automatically.

Recovery explicitly performs these steps without a surrounding transaction:

1. Retry each PENDING statistics journal using its stored closing metadata. Each failure is logged, remains
   pending and does not prevent the other dates from being attempted.
2. Resubmit incomplete Modulith publications targeted only at `statistics.shift-sales-history`, containing
   JournalClosedEvent, when their statistics date is absent or already PROCESSED. Absent dates cover a failed
   pending-marker write. Confirmed dates replay idempotently to finish the publication without reading mutable
   sources or overwriting history. Dates still PENDING were just attempted and wait until the next pass.

The existing unique keys, per-date row lock, REQUIRES_NEW writes and atomic whole-day confirmation remain
unchanged. Concurrent delivery/recovery cannot insert duplicates or downgrade a confirmed date. There is no
new migration, public contract, endpoint or change to another module. The pom declares the already existing
spring-modulith-events-core dependency at compile scope to use the typed publication target identifier; it
previously arrived at runtime through the JPA starter.

Explicit polling is enabled by default, with a 60-second initial delay and 60-second delay after each pass.
Configuration properties:

```properties
statistics.shift-sales.recovery.enabled=true
statistics.shift-sales.recovery.initial-delay-ms=60000
statistics.shift-sales.recovery.delay-ms=60000
```

An operator can also invoke `ShiftSaleHistoryRecoveryService.recoverPending()` through the application context.
No development database needs to be touched to verify recovery. The scheduled boundary logs database/registry
outages and allows the next pass to run. A process restart is not required and Modulith's automatic restart
republication property is not required. A restart alone with polling disabled does not retry these events.

For diagnosis, inspect PENDING rows in statistics_journal_sales (last_error, attempts), and incomplete
publications in event_publication with listener_id = 'statistics.shift-sales-history' and completion_date IS NULL.
A publication with no statistics row is also pending work. A completed publication and a PROCESSED date indicate
success; sale_count = 0 is a confirmed empty source result, never a substituted query error.

New tests:

- application/ShiftSaleHistoryRecoveryServiceTest.java: targeted replay and pending recovery selection.

- infrastructure/listeners/ShiftSaleHistoryEventIntegrationTest.java: actual JournalService closing and rollback,
